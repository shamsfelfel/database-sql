1 · The diagram, and the rules it carries١ · المخطّط، والقواعد التي يحملها

The manager asks two things every week: what did we take on 3 March? and which card payments came from which customer? The first is about every payment. The second is about one kind only. Whatever tables we build must answer both, and must refuse the rows the business forbids.

يسأل المدير كل أسبوع سؤالين: كم قبضنا يوم 3 مارس؟ وأيّ دفعات البطاقة جاءت من أيّ زبون؟ الأوّل عن كل المدفوعات، والثاني عن نوع واحد فقط. وأيًّا كانت الجداول التي نبنيها، فعليها أن تجيب عن السؤالين، وأن ترفض الصفوف التي يمنعها العمل.

The task: any set of tables for this model must keep the five rules below. A rule a table does not keep is a rule some clerk will break.

المهمّة: أيّ مجموعة جداول لهذا النموذج يجب أن تحفظ القواعد الخمس أدناه. والقاعدة التي لا يحفظها الجدول قاعدةٌ سيكسرها موظّف ما.

Which rule is drawn by the layout of the boxes, not by any #, * or line?

2 · Way 1: one table, a type column٢ · الطريقة 1: جدول واحد، وعمود للنوع

One table: the supertype becomes a single table, a method column says which subtype each row is, and every subtype's own column is made nullable.

الجدول الواحد: يصير النوع الأعلى جدولًا واحدًا، ويقول عمود method من أيّ نوع فرعي كل صفّ، ويُجعل كل عمود خاصّ بنوع فرعي قابلًا لـ null.

This is Lesson 1's one-entity model, and it had a defect: card_number cannot be NOT NULL, because cash rows have none. So R2, R3 and R4 cannot sit on single columns. They depend on method, and a rule across columns is a table-level CHECK.

هذا هو نموذج الكيان الواحد في الدرس 1، وكان فيه عيب: لا يمكن أن يكون card_number بقيد NOT NULL، لأن صفوف النقد بلا رقم. لذلك لا تستطيع R2 وR3 وR4 أن تجلس على أعمدة منفردة. فهي تعتمد على method، والقاعدة التي تربط أعمدة عدّة قيد CHECK على مستوى الجدول.

Step 2a · Write payments, rules and allالخطوة 2أ · اكتب payments بقواعدها كلها

customers(customer_id, name) exists. Create payments with payment_id, payment_date (DATE), amount, method (VARCHAR(11): 'CASH', 'CHECK' or 'CREDIT CARD'), card_number (VARCHAR(19)) and customer_id. The check inserts eleven rows, three legal and eight that break R1–R4, and wants exactly the three legal ones accepted.

الجدول customers(customer_id, name) موجود. أنشئ payments بالأعمدة payment_id، وpayment_date (DATE)، وamount، وmethod (VARCHAR(11): 'CASH' أو 'CHECK' أو 'CREDIT CARD')، وcard_number (VARCHAR(19))، وcustomer_id. يُدخل التصحيح أحد عشر صفًّا، ثلاثة منها سليمة وثمانية تكسر R1–R4، ولا يقبل إلا أن تُقبَل الثلاثة السليمة وحدها.

Show the answerاعرض الجواب 
CREATE TABLE payments (
  payment_id   NUMBER       PRIMARY KEY,
  payment_date DATE         NOT NULL,
  amount       NUMBER       NOT NULL,
  method       VARCHAR(11)  NOT NULL
               CHECK (method IN ('CASH', 'CHECK', 'CREDIT CARD')),
  card_number  VARCHAR(19),
  customer_id  NUMBER
               REFERENCES customers(customer_id),
  CHECK (   (method = 'CASH'        AND card_number IS NULL     AND customer_id IS NULL)
         OR (method = 'CHECK'       AND card_number IS NULL     AND customer_id IS NOT NULL)
         OR (method = 'CREDIT CARD' AND card_number IS NOT NULL AND customer_id IS NOT NULL))
);

One line of the last CHECK per subtype box: each says what that kind must have and must not have. The IN list is R5, but only for a single row: it lets no payment be two kinds, because one cell holds one value.

سطر واحد في قيد CHECK الأخير لكل صندوق نوع فرعي: كلٌّ منها يقول ما يجب أن يملكه ذلك النوع وما لا يجوز أن يملكه. وقائمة IN هي R5، لكن لصفّ واحد فقط: فلا تسمح لدفعة بأن تكون نوعين، لأن الخلية الواحدة تحمل قيمة واحدة.

Step 2b · The second question, in one tableالخطوة 2ب · السؤال الثاني، في جدول واحد

List every credit card payment with its payment_id, amount, card_number and the customer's name. Use exactly those four column names.

اعرض كل دفعة بطاقة ائتمان مع payment_id وamount وcard_number واسم الزبون name. استعمل أسماء الأعمدة الأربعة هذه بالضبط.

Show the answerاعرض الجواب 
SELECT p.payment_id, p.amount, p.card_number, c.name
FROM payments p
JOIN customers c ON c.customer_id = p.customer_id
WHERE p.method = 'CREDIT CARD';

Without the WHERE, the two cheques join to their customers too and four rows come back. In one table, asking about one kind always means filtering on the type column.

من دون WHERE يرتبط الشيكان بزبونيهما أيضًا، فتعود أربعة صفوف. وفي الجدول الواحد، السؤال عن نوع واحد يعني دائمًا التصفية على عمود النوع.

This browser engine stores a NULL typed into a NUMBER column as a value that is not null, so the CHECK above refuses VALUES (..., 'CASH', NULL, NULL). This lab leaves such columns out of the column list instead. Oracle treats the typed NULL as null and accepts the row.

يخزّن محرّك المتصفّح هذا قيمة NULL المكتوبة في عمود NUMBER على أنها قيمة غير فارغة، فيرفض قيد CHECK أعلاه الصفّ VALUES (..., 'CASH', NULL, NULL). لذلك يُسقط هذا المختبر هذه الأعمدة من قائمة الأعمدة بدلًا من ذلك. أمّا Oracle فيعامل NULL المكتوبة على أنها فارغة ويقبل الصفّ.

In way 1, where does R2, "a card payment must have a card number", live?

في الطريقة 1، أين تعيش R2، «يجب أن يكون لدفعة البطاقة رقم بطاقة»؟

NOT NULL would refuse every cash and cheque row. The * belongs to one subtype, so in one table it can only be stated together with the column that names the subtype.

قيد NOT NULL سيرفض كل صفوف النقد والشيكات. فعلامة * تخصّ نوعًا فرعيًّا واحدًا، ولذلك لا يمكن قولها في جدول واحد إلا مع العمود الذي يسمّي النوع الفرعي.

3 · Way 2: a table per subtype٣ · الطريقة 2: جدول لكل نوع فرعي

Way 1's rules hide in one long CHECK, and every column a new kind brings is empty for all the others. What if each kind had its own table, where its * is just NOT NULL?

قواعد الطريقة 1 مختبئة في قيد CHECK طويل واحد، وكل عمود يأتي به نوع جديد يبقى فارغًا في كل الأنواع الأخرى. فماذا لو كان لكل نوع جدوله، فتصير علامة * فيه مجرّد NOT NULL؟

A table per subtype: each subtype becomes its own table, repeating the supertype's columns, and no table stands for the supertype at all.

جدول لكل نوع فرعي: يصير كل نوع فرعي جدولًا مستقلًّا يكرّر أعمدة النوع الأعلى، ولا يمثّل النوع الأعلى أيُّ جدول على الإطلاق.

This is Lesson 1's three separate entities. Each table now states its own rules plainly, and cash_payments has no customer column at all, so R4 needs no constraint.

هذه هي الكيانات الثلاثة المنفصلة في الدرس 1. صار كل جدول يقول قواعده بوضوح، وليس في cash_payments عمود زبون أصلًا، فلا تحتاج R4 إلى أيّ قيد.

Step 3b · The first question, across three tablesالخطوة 3ب · السؤال الأوّل، عبر ثلاثة جداول

How many payments were taken on 3 March, and how much? Return one row with columns payments and taken. There is no table of all payments any more.

كم دفعة قُبضت يوم 3 مارس، وبكم؟ أعِد صفًّا واحدًا بعمودين payments وtaken. لم يعد هناك جدول لكل المدفوعات.

Show the answerاعرض الجواب 
SELECT COUNT(*) AS payments, SUM(amount) AS taken
FROM (SELECT payment_date, amount FROM cash_payments
      UNION ALL
      SELECT payment_date, amount FROM check_payments
      UNION ALL
      SELECT payment_date, amount FROM card_payments) AS k
WHERE payment_date = '2026-03-03';

The supertype has to be rebuilt inside the query before it can be asked anything. UNION ALL, not UNION: two cash payments of the same amount on the same day are two payments, and UNION would merge them into one.

يجب أن يُعاد بناء النوع الأعلى داخل الاستعلام قبل أن يُسأل عن أيّ شيء. UNION ALL لا UNION: فدفعتا نقد بالمبلغ نفسه في اليوم نفسه دفعتان، وUNION تدمجهما في واحدة.

Way 2 made R2, R3 and R4 simple column constraints. What did it pay for that?

4 · Way 3: a supertype table plus subtype tables٤ · الطريقة 3: جدول للنوع الأعلى مع جداول للأنواع الفرعية

Way 1 kept PAYMENT and lost the plain constraints. Way 2 kept the plain constraints and lost PAYMENT. The diagram has both: one outer box, and boxes inside it. Build what is drawn.

حفظت الطريقة 1 PAYMENT وخسرت القيود البسيطة. وحفظت الطريقة 2 القيود البسيطة وخسرت PAYMENT. أمّا المخطّط ففيه الاثنان: صندوق خارجي واحد، وصناديق داخله. ابنِ ما هو مرسوم.

Supertype plus subtypes: a table for the supertype holds the common columns, and each subtype table holds only its own, with a primary key that is also a foreign key to the supertype.

النوع الأعلى مع الأنواع الفرعية: جدول للنوع الأعلى يحمل الأعمدة المشتركة، وكل جدول نوع فرعي يحمل ما يخصّه وحده، بمفتاح أساسي هو أيضًا مفتاح أجنبي إلى النوع الأعلى.

This is the build Lesson 2 queried. Inheritance becomes a join on payment_id: a card_payments row gets its date and amount back from the payments row with the same key.

هذا هو البناء الذي استعلم منه الدرس 2. تصير الوراثة (inheritance) ربطًا على payment_id: يستعيد صفّ card_payments تاريخه ومبلغه من صفّ payments الذي يحمل المفتاح نفسه.

Step 4b · The second question, as inheritanceالخطوة 4ب · السؤال الثاني، على شكل وراثة

The same list as step 2b: payment_id, amount, card_number and name for every credit card payment. The amount lives in one table, the card number in another, the name in a third.

القائمة نفسها كما في الخطوة 2ب: payment_id وamount وcard_number وname لكل دفعة بطاقة ائتمان. المبلغ في جدول، ورقم البطاقة في آخر، والاسم في ثالث.

Show the answerاعرض الجواب 
SELECT p.payment_id, p.amount, k.card_number, c.name
FROM payments p
JOIN card_payments k ON k.payment_id = p.payment_id
JOIN customers c     ON c.customer_id = k.customer_id;

No WHERE: joining to card_payments is the filter, because only card payments have a row there. The first join is the inheritance; the second is the subtype's own relationship.

لا WHERE: فالربط مع card_payments هو التصفية، لأن دفعات البطاقة وحدها لها صفّ هناك. الربط الأوّل هو الوراثة، والثاني علاقة النوع الفرعي الخاصّة.

5 · The rule no column holds٥ · القاعدة التي لا يحملها أيّ عمود

Way 3 guards inwards-out. Outwards-in — every PAYMENT is a CASH, a CHECK or a CREDIT CARD — is R5, and nothing guards it. Payment 7 is entered and never filed under a kind; payment 4, already cash, is filed as a cheque too:

This box holds the two bad rows above. Write a query that returns, for every payment that is not in exactly one subtype table, its payment_id and kinds, the number of subtype tables it is in.

Show the answerاعرض الجواب 
SELECT payment_id, kinds
FROM (SELECT p.payment_id,
             (SELECT COUNT(*) FROM cash_payments  s WHERE s.payment_id = p.payment_id)
           + (SELECT COUNT(*) FROM check_payments s WHERE s.payment_id = p.payment_id)
           + (SELECT COUNT(*) FROM card_payments  s WHERE s.payment_id = p.payment_id) AS kinds
      FROM payments p) AS t
WHERE kinds <> 1;

Key takeawaysالخلاصة

  • A supertype and its subtypes have three builds: one table with a type column, a table per subtype, or a supertype table plus subtype tables.
  • للنوع الأعلى وأنواعه الفرعية ثلاثة أبنية: جدول واحد بعمود للنوع، أو جدول لكل نوع فرعي، أو جدول للنوع الأعلى مع جداول للأنواع الفرعية.
  • In one table, a subtype's * becomes a CHECK tied to the type column, never a plain NOT NULL.
  • في الجدول الواحد تصير علامة * الخاصّة بنوع فرعي قيد CHECK مربوطًا بعمود النوع، ولا تصير أبدًا NOT NULL بسيطًا.
  • A table per subtype drops the supertype: "all payments" needs UNION ALL, and IDs can repeat across kinds.
  • الجدول لكل نوع فرعي يُسقط النوع الأعلى: «كل المدفوعات» تحتاج إلى UNION ALL، والأرقام قد تتكرّر بين الأنواع.
  • In supertype-plus-subtypes, the subtype's primary key is also a foreign key to the supertype; inheritance is a join on it.
  • في بناء النوع الأعلى مع الأنواع الفرعية، المفتاح الأساسي للنوع الفرعي مفتاح أجنبي إلى النوع الأعلى أيضًا، والوراثة ربط عليه.
  • Exhaustive and mutually exclusive across tables are kept by an audit query that starts from the supertype.
  • الشمول والتنافي عبر الجداول يحفظهما استعلام تدقيق يبدأ من النوع الأعلى.

Mistakes to avoidأخطاء يجب تجنّبها

  • Declaring card_number NOT NULL in the single table — every cash payment is refused.
  • إعلان card_number NOT NULL في الجدول الواحد — فتُرفض كل دفعة نقدية.
  • Using UNION to rebuild the supertype — two equal payments become one.
  • استعمال UNION لإعادة بناء النوع الأعلى — فتصير الدفعتان المتساويتان دفعة واحدة.
  • Repeating payment_date in a subtype table of way 3 — the inherited attribute is stored twice and can disagree.
  • تكرار payment_date في جدول نوع فرعي في الطريقة 3 — فتُخزَّن الخاصية الموروثة مرّتين وقد تختلف القيمتان.
  • Auditing from the subtype tables — a payment filed nowhere is never found.
  • التدقيق انطلاقًا من جداول الأنواع الفرعية — فلا يُعثر أبدًا على الدفعة التي لم تُصنَّف في أيّ مكان.
